# Benchmarks

Measured engine performance and the decisions derived from it.

## Methodology

- Synthetic trees generated by `benchmarks/gen_tree.py`: seeded, ten
  languages (`.py .js .jsx .ts .tsx .rs .java .go .c .cpp .cs`), every file
  mixes real maintenance comments, code, and trap content (markers inside
  strings/raw strings/text blocks) so parsing work is honest. Large files
  use realistic bulk (big comment blocks, long strings) rather than
  pathological scope storms. Each tree carries a `.todoscope.json` enabling
  all ten languages, and a few nested `.gitignore` files.
- `benchmarks/run.py` measures the full engine (`scan_files`), one warmup
  plus 5 timed runs per mode, reporting **median and min**. Serial and
  worker counts {2, 4, 8, 16, 32}.
- Machine: Linux x86_64, **16 physical cores / 32 threads** (Ryzen 395),
  62.1 GiB RAM, Python 3.12.13, warm page cache. Cold-cache runs are
  possible with `sudo sysctl vm.drop_caches=3` first (the harness never
  runs sudo).

## Results (2026-08-13, all ten languages)

| Workload | Files | Size | Serial | 8 workers | 16 workers | 32 workers |
|---|---:|---:|---:|---:|---:|---:|
| tiny | 50 | 0.08 MiB | **15.0 ms** | 27.9 ms | 26.4 ms | 32.8 ms |
| many-small | 5000 | 10.9 MiB | 2.14 s | 0.63 s | **0.62 s** | 0.63 s |
| monorepo | 2000 | 4.3 MiB | 0.76 s | 0.25 s | **0.22 s** | 0.22 s |
| few-large | 8 | 15.3 MiB | **0.55 s** | 0.59 s | 0.58 s | 0.59 s |

## Reading the curve

- **Pool startup dominates small scans**: tiny (50 files) runs in 15 ms
  serially; every pool variant is 1.5–2x slower. Small scans must stay
  serial.
- **Many small files scale ~3.4x** (2.14 s → 0.62 s); **mixed monorepos
  scale ~3.5x** (0.76 s → 0.22 s). The plateau sits between 8 and 16
  workers; 32 is flat or slightly worse.
- **Few-large is the counterintuitive case**: 8 files of 2 MB each are
  FASTER serially than in any pool. Each 2 MB file produces ~33k findings,
  and serialising those result lists across process IPC costs more than the
  parallel parse saves. Pool benefit is therefore a function of FILE COUNT
  and finding density, not just total bytes.

## Decisions derived

Every engine constant is sweep-derived; the sweep data lives in
`benchmarks/.results/sweep-*.csv` and can be regenerated with
`uv run python benchmarks/sweep.py --kind {crossover,bytefloor,chunks}`.

### `PARALLEL_MIN_FILES = 500` — file-count crossover sweep

| Files | Serial | 8 workers | Speedup |
|---:|---:|---:|---:|
| 100 | 0.036 s | 0.054 s | 0.66x |
| 250 | 0.087 s | 0.085 s | 1.03x |
| 500 | **0.178 s** | **0.109 s** | **1.63x** |
| 750 | 0.292 s | 0.130 s | 2.25x |
| 1000 | 0.389 s | 0.143 s | 2.73x |
| 1500 | 0.588 s | 0.180 s | 3.28x |
| 2000 | 0.800 s | 0.262 s | 3.05x |

The pool loses at 100 files, breaks even at 250, and first clearly wins at
500 — which is why 500 is the gate.

### No byte floor — byte-size sweep

| Total size (1000 files) | Serial | 8 workers | Speedup |
|---:|---:|---:|---:|
| 0.10 MiB (100 B files) | 0.055 s | 0.023 s | 2.33x |
| 0.48 MiB | 0.117 s | 0.047 s | 2.47x |
| 1.91 MiB | 0.351 s | 0.129 s | 2.72x |
| 9.54 MiB | 1.582 s | 0.709 s | 2.23x |

Once the file count qualifies, the pool wins even for tiny files (and the
corner case 500 x 100 B still wins 1.28x). A total-byte threshold adds
nothing, so there is none.

### `SUBMIT_CHUNK_SIZE = 50` — chunk-size sweep (2000-file monorepo, 8 workers)

| Chunk | 50 | 100 | 200 | 500 | 1000 |
|---:|---:|---:|---:|---:|---:|
| Median | **0.193 s** | 0.216 s | 0.241 s | 0.337 s | 0.563 s |

Smaller chunks win (better load balancing, smaller IPC bursts); 50 is the
sweep's best measured value.

### `MAX_PARALLEL_WORKERS = 8` — workload plateau (main tables above)

many-small/monorepo plateau between 8 and 16 workers (16 buys at most 15%
on some workloads, 32 is flat or slower), and each worker costs a Python
runtime plus parser libraries.

### Not derivable from pools: the few-large counterexample

8 files of 2 MB each are FASTER serially than in any pool (0.55 s vs
0.57-0.59 s): each file produces ~33k findings and serialising those lists
across IPC costs more than the parallel parse saves. The count gate handles
this case automatically (8 files is far below 500).

## Running it yourself

```bash
uv run python benchmarks/run.py --preset tiny
uv run python benchmarks/run.py --preset many-small --split
uv run python benchmarks/run.py --cold   # prints drop-caches instructions
```

Trees live in `benchmarks/.trees/`, results in `benchmarks/.results/`
(both gitignored). See `benchmarks/README.md` for generator details.
